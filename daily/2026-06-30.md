## Interview Story 1: Benchmark Methodology

The first thing I can explain in an interview is that LLM serving benchmarks need careful methodology. My first vLLM smoke run had very high TTFT because the first request included warmup effects such as Triton JIT and runtime initialization. After adding warmup requests, steady-state TTFT dropped sharply. This taught me not to mix cold start and steady-state serving numbers.

I also fixed throughput measurement. Under concurrency, summing per-request latency is wrong because requests overlap in wall-clock time. The benchmark client should start the measured timer after warmup and compute output throughput as total server-reported completion tokens divided by measured wall-clock time.

Finally, I changed output-token counting to use vLLM's streaming `usage.completion_tokens` instead of estimating tokens from generated text. This matters because `max_tokens` is only an upper bound; the model may stop early, and whitespace counting is not tokenizer-accurate.

## Interview-Ready Answer

```text
I built a small vLLM benchmark client and learned that benchmark methodology matters a lot for LLM serving. First, I separated cold-start latency from steady-state latency by adding warmup requests, because the first request can include Triton JIT, CUDA graph capture, and runtime initialization. Second, I measured concurrent throughput using wall-clock time after warmup instead of summing per-request latencies, since concurrent requests overlap. Third, I used vLLM's streaming usage field to count completion tokens instead of estimating tokens from text. With these fixes, the benchmark could report TTFT, TPOT, latency percentiles, and output tokens per second more reliably.
```

## Concepts To Be Able To Explain

- TTFT means time to first token. It includes request admission, queueing, prefill, and the first decode step.
- TPOT means time per output token after the first token. It is a compact decode-speed metric.
- Latency is the full request time from send to finish.
- Throughput under concurrency should use total completed output tokens divided by measured wall-clock time.
- Warmup requests should be excluded from the measured window when reporting steady-state performance.
- p95 and p99 are important because scheduler and queueing problems often show up in the tail before they show up in averages.

## Beginner Review: Request Lifecycle

Before reviewing more experiment numbers, slow down and make sure the basic LLM serving path is clear:

```text
HTTP request
-> tokenizer
-> request queue
-> scheduler
-> prefill
-> KV cache write
-> decode loop
-> sampling
-> detokenizer
-> streaming response
```

The key beginner mental model is:

- Prefill processes the input prompt and mainly affects TTFT.
- Decode generates output tokens one by one and mainly affects TPOT and total latency.
- KV cache stores past attention keys and values so decode does not recompute the whole history.
- The scheduler decides which requests can run together and which requests must wait.
- High concurrency improves GPU utilization, but it can also increase queueing delay and tail latency.

Interview sentence:

```text
In an LLM server, a request is first tokenized and admitted by the scheduler. The prefill phase processes the prompt and writes the initial KV cache, which mostly affects TTFT. Then the decode loop generates tokens one by one using the KV cache, which mostly determines TPOT and total latency. The scheduler and KV-cache manager decide how many requests can run concurrently without exhausting GPU memory or hurting tail latency too much.
```

## Beginner Review: KV Cache

KV cache is saved attention state for previous tokens.

Beginner mental model:

```text
Without KV cache:
every new token recomputes old prompt/history work

With KV cache:
old K/V states are stored once and reused during decode
```

In transformer attention, each token creates Q, K, and V vectors:

- Q asks what information the current token needs.
- K helps match against previous tokens.
- V contains the information to reuse.

During decode, old tokens do not change, so their K/V can be cached. This is why KV cache speeds up generation.

The tradeoff:

```text
KV cache saves compute
but costs GPU memory
```

The cache grows with:

- prompt length,
- generated output length,
- number of concurrent requests,
- number of layers,
- hidden size / attention heads.

Interview sentence:

```text
KV cache stores the attention keys and values of previous tokens. During prefill, the server writes the initial K/V for the prompt. During decode, each new token reads the old K/V and appends its own K/V, so the model does not recompute the whole history every step. This makes decode much faster, but it turns LLM serving into a GPU memory management problem under long contexts and high concurrency.
```

## Beginner Review: Batching And Scheduling

Batching means grouping multiple requests into a larger GPU workload.

Without batching:

```text
request A runs
request B waits
request C waits
```

With batching:

```text
request A + request B + request C run together
```

This improves GPU utilization, but it can increase waiting time for some requests.

The scheduler decides:

- which requests run now,
- which requests wait,
- how many prompt tokens can enter prefill,
- how many decode tokens can run,
- whether there is enough KV cache capacity.

For LLMs, continuous batching is more useful than static batching because requests finish at different times. Finished requests can leave, new requests can enter, and the decode loop keeps moving.

Core tradeoff:

```text
better batching -> higher throughput
but sometimes worse TTFT or tail latency
```

Interview sentence:

```text
LLM serving uses batching to improve GPU utilization, but requests have variable prompt lengths and output lengths, so static batching is inefficient. Continuous batching lets finished requests leave and new requests enter while active decode continues. The scheduler decides which prefill and decode work to admit under KV-cache and token-budget limits, so scheduler tuning is a tradeoff between throughput, TTFT, and p95/p99 latency.
```

## Beginner Review: Tensor Parallel

Tensor parallel means splitting model computation inside a layer across multiple GPUs.

Beginner mental model:

```text
benefit: each GPU does less compute
cost: GPUs must communicate partial results
```

On `pink`, TP=2 improved throughput and tail latency, but not by 2x:

- concurrency 16 throughput: TP=1 about 710 tok/s, TP=2 about 1099 tok/s.
- p99 latency at concurrency 16: TP=1 about 765 ms, TP=2 about 506 ms.
- speedup was about 1.5-1.7x rather than 2x.

Reason:

```text
two RTX 4090 GPUs communicate over SYS/PCIe path, not NVLink
tensor parallel adds cross-GPU synchronization such as all-reduce
communication overhead offsets part of the compute gain
```

Chinese interview sentence:

```text
我在双 4090 上对比了 vLLM 的 TP=1 和 TP=2。TP=2 确实提升了吞吐和尾延迟，比如 concurrency 16 时吞吐从大约 710 tok/s 提升到 1099 tok/s，但没有达到 2 倍加速。原因是 tensor parallel 一方面把每层计算切到多张 GPU 上，降低单卡计算量；另一方面每层都可能需要跨卡通信和同步。pink 的两张 4090 是 SYS 拓扑，不是 NVLink，所以通信开销会抵消一部分计算收益。
```
