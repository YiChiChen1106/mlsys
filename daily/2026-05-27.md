## Concepts I Can Explain

- Official A100 validation is different from local 4090 sanity benchmarking.
- Popcorn `mode=test` checks correctness before leaderboard submission.
- A single-file `submission.py` must expose `custom_kernel(data)`.
- Reusing a partial-sum buffer can avoid repeated allocation overhead in benchmark loops.
- `num_warps` changes how much warp-level parallelism one Triton program uses internally.
- Atomic-add reduction removes the final reduction kernel but creates contention on one output address.
- CUDA inline exposes thread/block/warp/shared-memory control, but the official runner may impose stricter stream rules than local testing.
- Official-template CUDA inline can pass Popcorn; custom pybind-style inline did not.
- CUDA `THREADS x ITEMS_PER_THREAD` changes per-block work size, but this sweep did not expose a faster direction.
- CUDA atomic reduces final-stage work but introduces contention on one scalar output address.

- Popcorn rate limits make it useful to prepare correctness first, then run A100 batches after reset.
- CUDA atomic got close in best sample but not in mean, so it is not leaderboard-worthy yet.
- CUDA persistent with grid-stride loops improved over previous CUDA attempts and matched the accepted inline baseline at g512, but still not the Triton baseline.
